## 2. 八项功能的分阶段拆解

阶段划分：P1 身份与能力 → P2 请求与审查 → P3 审批与证据 → P4 适配器与控制台。
每项都写「做什么／怎么验／依赖什么／完成判据」。

### 2.1 Agent 注册与身份管理（P1）

- **做什么**：Agent 登记表（`agent_id`、显示名、公钥或共享密钥摘要、状态、创建时间、
  撤销时间）；身份校验用 HMAC-SHA256 签名，签名覆盖请求规范化串；撤销后一律拒绝。
- **怎么验**：注册后签名请求通过；未注册 `agent_id` 被拒；被撤销身份被拒；
  篡改签名被拒；同一 `nonce` 重放被拒。
- **依赖什么**：仅标准库 `hmac`／`hashlib`；不依赖网络、不依赖数据库服务。
- **完成判据**：四项反向用例（未注册／已撤销／签名篡改／重放）全部返回 `DENY` 或 `ERROR`，
  且每次拒绝都落一条证据记录；正向用例返回 `ALLOW`。

### 2.2 Agent 能力登记（P1）

- **做什么**：每个 Agent 声明能力清单（`capability_id`、允许的 `action_type`、
  允许的目标根、是否需要审批）；能力是**授权上限**，请求超出即拒。
- **怎么验**：声明 `file.delete` 且目标根 `workspace/approved` 的 Agent，删除该根内文件放行；
  删除根外文件被拒；请求未声明能力被拒；能力声明为空时任何写操作被拒。
- **依赖什么**：能力声明件（JSON）；与 2.1 的 `agent_id` 绑定。
- **完成判据**：能力越界用例全部 `DENY`；能力内用例 `ALLOW`；能力声明缺失时 `ERROR`（不静默放行）。

### 2.3 统一操作请求接口（P2）

- **做什么**：单一请求结构 `req/1`：`schema`、`agent_id`、`capability`、`action_type`、
  `target`、`params`、`nonce`、`ts`、`sig`。所有 Agent 只能通过这一个入口提交。
- **怎么验**：合法请求被解析并进入审查；缺字段、字段类型错、`schema` 不符时返回 `ERROR`；
  同一请求重复提交（同 `nonce`）返回 `DENY`。
- **依赖什么**：2.1 的身份校验；2.2 的能力声明。
- **完成判据**：结构校验的 6 类反例全部 `ERROR`／`DENY`，且错误码可查；合法请求 100% 进入审查。

### 2.4 执行前规则审查（P2）

- **做什么**：请求进入既有规则审查链，按「身份 → 能力 → 路径形态 → 范围 → 规则命中」顺序判定，
  输出五值决策之一：`ALLOW`／`DENY`／`REQUIRE_APPROVAL`／`WARNING`／`ERROR`。
- **怎么验**：对同一目标分别构造五类输入，逐个拿到预期决策；决策必须带 `rule_id`
  （口径沿用 0.2：本记录的决定性检查项 id）。
- **依赖什么**：
  - `gate_registry` 的注册完整性口径（复用，不重写）；
  - 0.2 的 S0 检查项语义（`S0.1` 意图有效、`S0.2` 动作允许、`S0.3` 路径形态、
    `S0.4` 范围判定、`S0.5` 基线一致、`S0.6` 票可用）；
  - `rule_id` 口径：`supervisor._rule_id` 的取值规则。
- **完成判据**：五值决策各有一条实跑记录可查；不允许出现「决策为空」或「默认放行」；
  审查函数抛异常时结果为 `ERROR` 而非 `ALLOW`。

### 2.5 人工审批接口（P3）

- **做什么**：`REQUIRE_APPROVAL` 决策落一条待批记录（`approval_state=pending`），
  审批人给出批准／拒绝后追加一条审批结果记录（`approval_state=approved/rejected`），
  原记录**不回改**（只追加）。
- **怎么验**：越界请求得到 `REQUIRE_APPROVAL`；未批准前重试仍为 `REQUIRE_APPROVAL`；
  批准后同请求放行；拒绝后同请求为 `DENY`；批准记录与原记录可通过 `op_id` 关联。
- **依赖什么**：2.6 账本（追加语义）；2.1 身份（审批人身份）。
- **完成判据**：`pending→approved` 与 `pending→rejected` 两条路径各有可回查记录；
  原记录字节不变（哈希链验通过）。

### 2.6 Agent 操作证据记录（P3）

- **做什么**：每条动作落一行 `act/1` 记录，字段至少含：Agent 身份、请求摘要、
  时间、规则版本、命中规则、决策、审批结果占位、异常。
  关联键沿用 0.2 四外键：`op_id`／`run_id`／`rule_id`／`error_code`。
- **怎么验**：账本 `verify()` 无断点；每条记录四外键齐全；按 `op_id` 能查回；
  篡改任一行后 `verify()` 报出具体断点行号。
- **依赖什么**：0.2 `jiancha/ledger.py` 的 `ActionLedger`（**整件复用**，不改逻辑）。
- **完成判据**：`verify().break == ''`；记录数＝实际动作数；篡改反向用例能定位到行号。

### 2.7 Agent 接入适配器（P4）

- **做什么**：把统一请求转成内核可审查的动作（`action_type`／`target`／`params`），
  提供至少一个真实宿主示例（如 personal 的 MCP dispatch 或一个文件操作宿主）。
- **怎么验**：适配器接入后跑一条正向链路（请求→审查→决策→记录）；拔掉适配器时不产生
  第二条路径；适配器不得自行放宽决策。
- **依赖什么**：2.3、2.4；宿主已有的 `capability.check`／`output_guard` 挂点。
- **完成判据**：接入示例可重复跑，输出稳定；适配器内**不出现**任何 `if decision: pass` 式放宽。

### 2.8 治理状态与查询控制台（P4）

- **做什么**：只读查询面：按 `agent_id`／`op_id`／决策／时间查记录；显示链完整性、
  记录总数、待批队列；**不提供写操作**。
- **怎么验**：查询结果与账本行数一致；链断裂时页面／命令显示为红；待批队列数与
  `approval_state=pending` 条数一致。
- **依赖什么**：2.6 账本；无额外服务依赖（先做 CLI，后做页面）。
- **完成判据**：查询结果可核对（条数、哈希、断点）；只读性可证（无新增／修改行）。

## 3. beta1 最小骨架（今日交付）

### 3.1 定义

beta1＝**能跑起来的最小骨架**，交付以「五步链路真跑通」为准，不以文档或空函数充数。

五步链路：

1. 示例 Agent 以统一请求结构提交一条操作（示例：删除某文件）；
2. 内核识别 Agent 身份与声明的能力；
3. 走既有规则审查，返回明确决策（`ALLOW`／`DENY`／`REQUIRE_APPROVAL`／`WARNING`／`ERROR`）；
4. 生成一条证据记录（Agent 身份、请求、时间、规则版本、命中规则、决策、审批结果占位、异常）；
5. 能从记录里查回来。

### 3.2 beta1 完成判据

- 五步每一步都有实测输出与 rc，且 rc 与结论一致；
- 反向用例：未注册身份、能力越界、签名篡改，至少三类被拒并各留一条记录；
- 账本 `verify()` 无断点；
- 全链路不修改 core 仓、不改三端、不升版本、不打 tag、不推送。

### 3.3 beta1 明确不做

- 不做 Web 控制台（只做 CLI 查询）；
- 不做多进程并发与锁；
- 不做网络／MCP 生产接线（只做可替换的适配器接口与示例）；
- 不做审批人身份体系（审批结果用占位字段，不做签名）。

## 2. Stage-by-stage breakdown of the eight functions

Stage division: P1 identity and capability → P2 request and review → P3 approval and evidence → P4 adapters and console.
Each item states "what to do / how to verify / what it depends on / completion criteria".

### 2.1 Agent registration and identity management (P1)

- **What to do**: Agent registry table (`agent_id`, display name, public key or shared-key digest, status, creation time,
  revocation time); identity verification uses HMAC-SHA256 signatures, and the signature covers the canonicalized request string; once revoked, requests are always rejected.
- **How to verify**: after registration, a signed request passes; an unregistered `agent_id` is rejected; a revoked identity is rejected;
  a tampered signature is rejected; a replayed `nonce` is rejected.
- **What it depends on**: only the standard library `hmac` / `hashlib`; no network dependency, no database service dependency.
- **Completion criteria**: all four negative cases (unregistered / revoked / tampered signature / replay) return `DENY` or `ERROR`,
  and every rejection writes one evidence record; the positive case returns `ALLOW`.

### 2.2 Agent capability registration (P1)

- **What to do**: each Agent declares a capability list (`capability_id`, allowed `action_type`,
  allowed target root, whether approval is required); capability is an **authorization ceiling**, and any request beyond it is rejected.
- **How to verify**: an Agent that declares `file.delete` with target root `workspace/approved` is allowed to delete files inside that root;
  deleting a file outside the root is rejected; a request for an undeclared capability is rejected; when the capability declaration is empty, any write operation is rejected.
- **What it depends on**: the capability declaration file (JSON); bound to the `agent_id` from 2.1.
- **Completion criteria**: all out-of-bounds cases return `DENY`; in-bounds cases return `ALLOW`; a missing capability declaration returns `ERROR` (never silently allowed).

### 2.3 Unified operation request interface (P2)

- **What to do**: a single request structure `req/1`: `schema`, `agent_id`, `capability`, `action_type`,
  `target`, `params`, `nonce`, `ts`, `sig`. All Agents may submit only through this single entry point.
- **How to verify**: a legal request is parsed and enters review; a missing field, a wrong field type, or a `schema` mismatch returns `ERROR`;
  submitting the same request again (same `nonce`) returns `DENY`.
- **What it depends on**: identity verification from 2.1; the capability declaration from 2.2.
- **Completion criteria**: all 6 classes of structural-validation counterexamples return `ERROR` / `DENY`, and the error codes are queryable; 100% of legal requests enter review.

### 2.4 Pre-execution rule review (P2)

- **What to do**: the request enters the existing rule review chain and is decided in the order "identity → capability → path form → scope → rule hit",
  outputting one of the five decisions: `ALLOW` / `DENY` / `REQUIRE_APPROVAL` / `WARNING` / `ERROR`.
- **How to verify**: construct five classes of input against the same target and obtain the expected decision for each one; the decision must carry `rule_id`
  (definition inherited from 0.2: the id of the decisive check item for this record).
- **What it depends on**:
  - the registration-completeness definition of `gate_registry` (reused, not rewritten);
  - the semantics of the 0.2 S0 check items (`S0.1` intent valid, `S0.2` action allowed, `S0.3` path form,
    `S0.4` scope determination, `S0.5` baseline consistent, `S0.6` ticket usable);
  - the `rule_id` definition: the value rule of `supervisor._rule_id`.
- **Completion criteria**: each of the five decisions has one actual run record that can be queried; "empty decision" or "allow by default" must not occur;
  when the review function raises an exception, the result is `ERROR` rather than `ALLOW`.

### 2.5 Manual approval interface (P3)

- **What to do**: a `REQUIRE_APPROVAL` decision writes one pending-approval record (`approval_state=pending`);
  after the approver gives an approval or rejection, one approval-result record is appended (`approval_state=approved/rejected`);
  the original record is **not modified** (append only).
- **How to verify**: an out-of-bounds request gets `REQUIRE_APPROVAL`; retrying before approval still gets `REQUIRE_APPROVAL`;
  after approval the same request is released; after rejection the same request gets `DENY`; the approval record and the original record are linked via `op_id`.
- **What it depends on**: the ledger in 2.6 (append semantics); identity from 2.1 (approver identity).
- **Completion criteria**: both the `pending→approved` and the `pending→rejected` paths have queryable records;
  the original record is byte-for-byte unchanged (the hash chain verifies).

### 2.6 Agent operation evidence recording (P3)

- **What to do**: each action writes one `act/1` record line, whose fields include at least: Agent identity, request digest,
  time, rule version, hit rule, decision, approval result placeholder, exception.
  The association keys follow the 0.2 four foreign keys: `op_id` / `run_id` / `rule_id` / `error_code`.
- **How to verify**: ledger `verify()` reports no break point; every record has all four foreign keys; records can be queried back by `op_id`;
  after tampering with any row, `verify()` reports the specific break row number.
- **What it depends on**: the `ActionLedger` of 0.2 `jiancha/ledger.py` (**reused as a whole**, logic unchanged).
- **Completion criteria**: `verify().break == ''`; record count = actual action count; the tampering negative case can locate the row number.

### 2.7 Agent integration adapters (P4)

- **What to do**: convert the unified request into an action the kernel can review (`action_type` / `target` / `params`),
  and provide at least one real host example (such as personal's MCP dispatch or a file-operation host).
- **How to verify**: after the adapter is integrated, run one positive chain (request → review → decision → record); when the adapter is removed,
  no second path is produced; the adapter must not loosen decisions on its own.
- **What it depends on**: 2.3, 2.4; the host's existing `capability.check` / `output_guard` hook points.
- **Completion criteria**: the integration example can be rerun repeatably with stable output; inside the adapter **no** `if decision: pass`-style loosening appears.

### 2.8 Governance status and query console (P4)

- **What to do**: a read-only query surface: query records by `agent_id` / `op_id` / decision / time; display chain integrity,
  total record count, and the pending-approval queue; **no write operations are provided**.
- **How to verify**: query results match the ledger row count; when the chain is broken, the page / command shows red; the pending-approval queue count matches
  the number of `approval_state=pending` rows.
- **What it depends on**: the ledger in 2.6; no additional service dependency (CLI first, page later).
- **Completion criteria**: query results can be checked (counts, hashes, break points); the read-only property is provable (no new or modified rows).

## 3. beta1 minimum skeleton (delivered today)

### 3.1 Definition

beta1 = **the minimum skeleton that can run**; delivery is judged by "the five-step chain truly runs through", not padded out with documents or empty functions.

The five-step chain:

1. An example Agent submits one operation using the unified request structure (example: delete a file);
2. The kernel identifies the Agent's identity and declared capability;
3. It goes through the existing rule review and returns an explicit decision (`ALLOW` / `DENY` / `REQUIRE_APPROVAL` / `WARNING` / `ERROR`);
4. One evidence record is generated (Agent identity, request, time, rule version, hit rule, decision, approval result placeholder, exception);
5. It can be queried back from the record.

### 3.2 beta1 completion criteria

- Each of the five steps has measured output and an rc, and the rc agrees with the conclusion;
- Negative cases: unregistered identity, capability out of bounds, tampered signature — at least three classes are rejected and each leaves one record;
- Ledger `verify()` reports no break point;
- The whole chain does not modify the core repository, does not change the three clients, does not bump the version, does not tag, does not push.

### 3.3 Explicitly not done in beta1

- No Web console (CLI query only);
- No multi-process concurrency or locking;
- No network / MCP production wiring (only replaceable adapter interfaces and examples);
- No approver identity system (approval results use placeholder fields, with no signatures).
