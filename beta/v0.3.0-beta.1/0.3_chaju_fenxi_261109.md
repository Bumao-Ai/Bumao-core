## 二、逐项（原文级别，不压缩）

### 2.1 Agent 注册与身份管理 —— 没有

- **现状**：core 里没有「Agent」这个主体。身份相关只有意图单上的 `approved_by`：
  `scope.py:110` 要求非空，`:53` 判断代理代签，`:57` 判弱授权。
- **覆盖了什么**：人的审批身份、代理代签的弱授权标记。
- **没有覆盖什么**：Agent 登记表、Agent 标识、Agent 状态（active/revoked）、
  Agent 侧密钥或签名、Agent 与意图单的绑定关系。
- **0.3 要补**：注册／撤销／绑定；否则「谁在操作」只能靠 `approved_by`，无法区分多个 Agent。

### 2.2 Agent 能力登记 —— 没有

- **现状**：scope 的 `under/denied/in_scope`（`scope.py:198/205/217`）约束的是**一次任务的
  `workspace` 与 `approved_roots/approved_files`**，不是 Agent 的长期能力。
- **覆盖了什么**：单次授权范围内的目标判定。
- **没有覆盖什么**：能力清单（`capability_id`、动作类型、目标根、是否需审批）、
  能力与请求的对账、能力缺失时的硬拒。
- **风险**：若直接用 scope 代替能力，等于把「能力」退化成「每单重批」，Agent 无法被长期治理。

### 2.3 统一操作请求接口 —— 部分已有

- **现状**：`intent/1` 意图单由 `load_order`（`scope.py:81`）装载、
  `validate_order`（`:171`）校验；动作以 `action` 字典进 `Supervisor.run_action`（`supervisor.py:448`）。
- **覆盖了什么**：请求合法性校验（schema、order_id、approved_by、批准集合、allowed_actions、
  expires_at、ticket_tid）；动作进入审查的路径。
- **没有覆盖什么**：面向 Agent 的**唯一提交结构**（Agent 身份、能力、动作、目标、nonce、签名）；
  没有 nonce 防重放；没有 Agent 侧签名校验。
- **0.3 要补**：`req/1` 统一结构与唯一入口，`intent/1` 降为「授权依据」继续复用。

  发布审批覆盖 `approval_covers_file`（`gate_registry.py:303`）、`version_approval`（`:328`）。

- **覆盖了什么**：账本链、动作级字段、证据包、票快照。

  `loader.py:14` `mode`、`:20` `is_enabled`、`:24` `load_if_enabled` 控制默认 off、延迟导入。

- **没有覆盖什么**：通用 Agent 适配器契约（任意 Agent 提交 `req/1`）、community/minimal 的接入、
  Agent 侧身份注入。
- **结论**：适配器**模式可复用**，但覆盖面只是 personal 一个端。

## 四、冲突清单（需用户裁定，不自行取舍）

### 冲突 C1：Agent 统一请求接口 vs「内核不提供任何服务／SDK／IPC」

- 依据：`bumao_core/HOST_CONTRACT.md:156-168`，尤其 `:162`
  「任何服务／SDK／IPC ｜ 内核全部 `.py` 内无 `http`／`socket`／`grpc`／`daemon`／`server`／`api`」，
  `:168`「不是应用运行时……只会调它做一次 check」。
- 冲突点：0.3 的「统一操作请求接口」「Agent 接入适配器」「治理查询控制台」若做成
  对外服务／SDK／IPC，与上述硬边界直接矛盾。
- 不裁定的后果：实现方式一旦选错（进程内 API 还是服务），要么违反契约，要么推翻规划。
- 待用户裁定：0.3 的「接口」是否限定为**进程内 Python 调用**（不出现 http/socket/grpc/daemon/server/api）。

### 冲突 C2：Agent 身份体系 vs「12 成员契约」不包含 Agent

- 依据：`HOST_CONTRACT.md:104` 12 成员契约与正文成员表（`:89-91`）。
- 冲突点：12 成员里没有任何 Agent 身份／能力成员位；0.3 新增 Agent 注册与能力登记，
  若要求宿主实现新成员，等于**扩契约**。
- 待用户裁定：新增成员是「可选扩展」（走 `getattr` 兜底），还是升级为契约必需（会破坏现有三端）。

### 冲突 C3：五值决策 vs 0.2 四值结果口径

- 依据：`supervisor.py:157/460/492/518/764` 的 `result ∈ {ok, denied, error, interrupted}`。
- 冲突点：0.3 要求 `ALLOW/DENY/REQUIRE_APPROVAL/WARNING/ERROR`；若直接改 0.2 的 `result` 值域，
  会动到既有判据与票面（用户明令不许改判据）。
- 待用户裁定：五值是否作为**新增字段**（如 `decision`）与 `result` 并存，而不是替换。

### 冲突 C4：`rule_id` 四外键 vs 动作记录实际未落 `rule_id`

- 依据：`ledger.py:6` 宣称五关联键含 `rule_id`；`:104` 只在票快照读取；
  `supervisor.py:177-197` 动作记录无 `rule_id`。
- 冲突点：0.3 若按「四外键齐全」设计，会在动作记录层发现 `rule_id` 缺失，与文档口径不符。
- 待用户裁定：是「补落到动作记录」，还是「把既有文档口径改为票快照层」。

## II. Item by item (original-text level, not compressed)

### 2.1 Agent registration and identity management — does not exist

- **Current state**: there is no "Agent" subject in core. The only identity-related item is `approved_by` on the intent form:
  `scope.py:110` requires it to be non-empty, `:53` judges proxy sign-off, `:57` judges weak authorization.
- **What is covered**: a person's approval identity, the weak-authorization mark of proxy sign-off.
- **What is not covered**: Agent registry table, Agent identifier, Agent status (active/revoked),
  Agent-side key or signature, the binding relationship between Agent and intent form.
- **What 0.3 must add**: register / revoke / bind; otherwise "who is operating" can only rely on `approved_by` and multiple Agents cannot be distinguished.

### 2.2 Agent capability registration — does not exist

- **Current state**: scope's `under/denied/in_scope` (`scope.py:198/205/217`) constrain **the
  `workspace` and `approved_roots/approved_files` of a single task**, not the Agent's long-term capability.
- **What is covered**: target determination within a single authorization scope.
- **What is not covered**: capability list (`capability_id`, action type, target root, whether approval is needed),
  reconciliation between capability and request, hard rejection when capability is missing.
- **Risk**: if scope is used directly in place of capability, that degrades "capability" into "re-approve for every order", and the Agent cannot be governed long-term.

### 2.3 Unified operation request interface — partially exists

- **Current state**: the `intent/1` intent form is loaded by `load_order` (`scope.py:81`) and
  validated by `validate_order` (`:171`); actions enter `Supervisor.run_action` (`supervisor.py:448`) as an `action` dict.
- **What is covered**: request legality validation (schema, order_id, approved_by, approval set, allowed_actions,

## IV. Conflict list (requires a user ruling; do not decide on your own)

### Conflict C1: Agent unified request interface vs "the kernel provides no services / SDK / IPC"

- Basis: `bumao_core/HOST_CONTRACT.md:156-168`, especially `:162`
  "any service / SDK / IPC | no `http` / `socket` / `grpc` / `daemon` / `server` / `api` in any kernel `.py`",
  `:168` "it is not an application runtime ... it only calls it to do one check".
- Point of conflict: if 0.3's "unified operation request interface", "Agent integration adapter", and "governance query console" are made into
  external services / SDK / IPC, they directly contradict the hard boundaries above.
- Consequence of not ruling: once the implementation approach is chosen wrongly (in-process API or service), either the contract is violated or the plan is overturned.
- Awaiting user ruling: whether 0.3's "interface" is limited to **in-process Python calls** (with no http/socket/grpc/daemon/server/api appearing).

### Conflict C2: Agent identity system vs "the 12-member contract" not including Agents

- Basis: `HOST_CONTRACT.md:104` the 12-member contract and the member table in the body (`:89-91`).
- Point of conflict: the 12 members have no slot for any Agent identity / capability member; 0.3 adds Agent registration and capability registration,
  and if it requires hosts to implement a new member, that equals **expanding the contract**.
- Awaiting user ruling: whether the new member is an "optional extension" (falling back via `getattr`), or is upgraded to a contract requirement (which would break the existing three clients).

### Conflict C3: Five-value decision vs the 0.2 four-value result definition

- Basis: `supervisor.py:157/460/492/518/764` with `result ∈ {ok, denied, error, interrupted}`.
- Point of conflict: 0.3 requires `ALLOW/DENY/REQUIRE_APPROVAL/WARNING/ERROR`; if the 0.2 `result` value domain is changed directly,
  it will touch the existing criteria and the ticket surface (the user has explicitly forbidden changing criteria).
- Awaiting user ruling: whether the five values coexist with `result` as a **new field** (e.g. `decision`) rather than replacing it.

### Conflict C4: The `rule_id` four foreign keys vs action records actually not carrying `rule_id`

- Basis: `ledger.py:6` claims the five association keys include `rule_id`; `:104` reads it only in the ticket snapshot;
  `supervisor.py:177-197` action records have no `rule_id`.
- Point of conflict: if 0.3 is designed on "all four foreign keys present", it will find `rule_id` missing at the action-record layer, inconsistent with the documented definition.
- Awaiting user ruling: whether to "add it to the action record" or "change the existing documented definition to the ticket-snapshot layer".
