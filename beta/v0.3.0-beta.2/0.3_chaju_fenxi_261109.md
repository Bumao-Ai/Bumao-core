## 二、逐项（原文级别，不压缩）

### 2.1 Agent 注册与身份管理 —— 没有

- **现状**：core 里没有「Agent」这个主体。身份相关只有意图单上的 `approved_by`：
  `scope.py:110` 要求非空，`:53` 判断代理代签，`:57` 判弱授权。
- **覆盖了什么**：人的审批身份、代理代签的弱授权标记。
- **没有覆盖什么**：Agent 登记表、Agent 标识、Agent 状态（active/revoked）、
  Agent 侧密钥或签名、Agent 与意图单的绑定关系。
- **0.3 要补**：注册／撤销／绑定；否则「谁在操作」只能靠 `approved_by`，无法区分多个 Agent。

### 2.2 Agent 能力登记 —— 没有

- **现状**：scope 的 `under/denied/in_scope`（`scope.py:198/205/217`）约束的是**一次任务的
  `workspace` 与 `approved_roots/approved_files`**，不是 Agent 的长期能力。
- **覆盖了什么**：单次授权范围内的目标判定。
- **没有覆盖什么**：能力清单（`capability_id`、动作类型、目标根、是否需审批）、
  能力与请求的对账、能力缺失时的硬拒。
- **风险**：若直接用 scope 代替能力，等于把「能力」退化成「每单重批」，Agent 无法被长期治理。

### 2.3 统一操作请求接口 —— 部分已有

- **现状**：`intent/1` 意图单由 `load_order`（`scope.py:81`）装载、
  `validate_order`（`:171`）校验；动作以 `action` 字典进 `Supervisor.run_action`（`supervisor.py:448`）。
- **覆盖了什么**：请求合法性校验（schema、order_id、approved_by、批准集合、allowed_actions、
  expires_at、ticket_tid）；动作进入审查的路径。
- **没有覆盖什么**：面向 Agent 的**唯一提交结构**（Agent 身份、能力、动作、目标、nonce、签名）；
  没有 nonce 防重放；没有 Agent 侧签名校验。
- **0.3 要补**：`req/1` 统一结构与唯一入口，`intent/1` 降为「授权依据」继续复用。

  live 下 `expires_at` 必填且 ≤24h（`:141-164`）；中断后 `resume(approval_path)`（`supervisor.py:724`）；
  发布审批覆盖 `approval_covers_file`（`gate_registry.py:303`）、`version_approval`（`:328`）。
- **覆盖了什么**：事前授权单签批、续跑审批、发布审批。
- **没有覆盖什么**：**动作级待批队列**（`pending→approved/rejected`）、审批人与 Agent 请求的
  一对一关联、批准前的重复请求仍判待批。
- **风险**：0.3 若把「续跑审批」当「人工审批」，会漏掉「一条请求卡在待批、后续同请求不得放行」。

  scope/checks/result/error_code/error_text/evidence/ticket/pid`；证据包 `_write_bundle`（`:621`）。
- **覆盖了什么**：账本链、动作级字段、证据包、票快照。
- **没有覆盖什么**：`agent_id`、`agent_status`、`capability`、`request_sha256`、`rule_id`（动作记录级）、
  `approval` 占位、`exception`。
- **结论**：账本能力**直接复用**，只扩展记录字段，不新造账本。

### 2.7 Agent 接入适配器 —— 部分已有

- **现状**：`PersonalAdapter`（`personal_adapter.py:66`）挂 personal 的 MCP 工具：
  `map_tool`（`:126`）做工具→动作映射，`invoke`（`:139`）、`_gated`（`:199`）分模式处理；
  `loader.py:14` `mode`、`:20` `is_enabled`、`:24` `load_if_enabled` 控制默认 off、延迟导入。
- **覆盖了什么**：一个真实宿主（personal MCP）的适配范式：默认 off、单挂载点、映射表。
- **没有覆盖什么**：通用 Agent 适配器契约（任意 Agent 提交 `req/1`）、community/minimal 的接入、
  Agent 侧身份注入。
- **结论**：适配器**模式可复用**，但覆盖面只是 personal 一个端。

### 2.8 治理状态与查询控制台 —— 部分已有

  `engine.py:663` `cmd_show`、`:430` `cmd_check` 输出体检。
- **覆盖了什么**：CLI 文本级状态与计数。
- **没有覆盖什么**：只读查询面（按 `agent_id/op_id/decision/时间` 查）、链完整性可视化、

- **风险**：0.3 若直接复用 `status()` 当「控制台」，会把内部运行态暴露成治理查询，语义不对。

## 四、冲突清单（需用户裁定，不自行取舍）

### 冲突 C1：Agent 统一请求接口 vs「内核不提供任何服务／SDK／IPC」

- 依据：`bumao_core/HOST_CONTRACT.md:156-168`，尤其 `:162`
  「任何服务／SDK／IPC ｜ 内核全部 `.py` 内无 `http`／`socket`／`grpc`／`daemon`／`server`／`api`」，
  `:168`「不是应用运行时……只会调它做一次 check」。
- 冲突点：0.3 的「统一操作请求接口」「Agent 接入适配器」「治理查询控制台」若做成
  对外服务／SDK／IPC，与上述硬边界直接矛盾。
- 不裁定的后果：实现方式一旦选错（进程内 API 还是服务），要么违反契约，要么推翻规划。
- 待用户裁定：0.3 的「接口」是否限定为**进程内 Python 调用**（不出现 http/socket/grpc/daemon/server/api）。

### 冲突 C2：Agent 身份体系 vs「12 成员契约」不包含 Agent

- 依据：`HOST_CONTRACT.md:104` 12 成员契约与正文成员表（`:89-91`）。
- 冲突点：12 成员里没有任何 Agent 身份／能力成员位；0.3 新增 Agent 注册与能力登记，
  若要求宿主实现新成员，等于**扩契约**。
- 待用户裁定：新增成员是「可选扩展」（走 `getattr` 兜底），还是升级为契约必需（会破坏现有三端）。

### 冲突 C3：五值决策 vs 0.2 四值结果口径

- 依据：`supervisor.py:157/460/492/518/764` 的 `result ∈ {ok, denied, error, interrupted}`。
- 冲突点：0.3 要求 `ALLOW/DENY/REQUIRE_APPROVAL/WARNING/ERROR`；若直接改 0.2 的 `result` 值域，
  会动到既有判据与票面（用户明令不许改判据）。
- 待用户裁定：五值是否作为**新增字段**（如 `decision`）与 `result` 并存，而不是替换。

### 冲突 C4：`rule_id` 四外键 vs 动作记录实际未落 `rule_id`

- 依据：`ledger.py:6` 宣称五关联键含 `rule_id`；`:104` 只在票快照读取；
  `supervisor.py:177-197` 动作记录无 `rule_id`。
- 冲突点：0.3 若按「四外键齐全」设计，会在动作记录层发现 `rule_id` 缺失，与文档口径不符。
- 待用户裁定：是「补落到动作记录」，还是「把既有文档口径改为票快照层」。

## II. Item by item (at source-text granularity, not compressed)

### 2.1 Agent registration and identity management —— absent

- **Current state**: there is no "Agent" subject in core. The only identity-related thing is `approved_by` on the intent order:
  `scope.py:110` requires it to be non-empty, `:53` judges proxy signing, `:57` judges weak authorization.
- **What it covers**: the approval identity of a person, and the weak-authorization marker for proxy signing.
- **What it does not cover**: the Agent registry, Agent identifiers, Agent status (active/revoked),
  Agent-side keys or signatures, and the binding relationship between an Agent and an intent order.
- **What 0.3 must add**: registration / revocation / binding; otherwise "who is operating" can only rely on `approved_by`, and multiple Agents cannot be distinguished.

### 2.2 Agent capability registration —— absent

- **Current state**: `under/denied/in_scope` of scope (`scope.py:198/205/217`) constrain **the `workspace` and
  `approved_roots/approved_files` of a single task**, not an Agent's long-term capabilities.
- **What it covers**: target determination within a single authorization scope.
- **What it does not cover**: the capability inventory (`capability_id`, action type, target root, whether approval is required),
  reconciliation between capabilities and requests, and hard rejection when a capability is missing.
- **Risk**: if scope is used directly in place of capabilities, "capability" degenerates into "re-approval for every order", and an Agent cannot be governed over the long term.

### 2.3 Unified operation request interface —— partially present

- **Current state**: the `intent/1` intent order is loaded by `load_order` (`scope.py:81`) and
  validated by `validate_order` (`:171`); the action enters `Supervisor.run_action` (`supervisor.py:448`) as an `action` dictionary.
- **What it covers**: request validity checks (schema, order_id, approved_by, approval set, allowed_actions,
  expires_at, ticket_tid); the path by which an action enters review.
- **What it does not cover**: a **unique submission structure** for Agents (Agent identity, capability, action, target, nonce, signature);
  there is no nonce replay protection; there is no Agent-side signature verification.
- **What 0.3 must add**: a `req/1` unified structure and a unique entry point, with `intent/1` downgraded to "authorization basis" and continuously reused.

### 2.4 Pre-execution rule review —— partially present

### 2.5 Human approval interface —— partially present

- **Current state**: `approved_by` is mandatory (`scope.py:110`), proxy signing requires a quotation (`:113`), and
  under live `expires_at` is mandatory and ≤24h (`:141-164`); after an interruption `resume(approval_path)` (`supervisor.py:724`);
  release approval covers `approval_covers_file` (`gate_registry.py:303`) and `version_approval` (`:328`).
- **What it covers**: prior authorization order signing, resume-run approval, release approval.
- **What it does not cover**: an **action-level pending-approval queue** (`pending→approved/rejected`), a one-to-one association between
  the approver and the Agent request, and repeated requests still being judged as pending before approval.
- **Risk**: if 0.3 treats "resume-run approval" as "human approval", it will miss "a request stuck in pending approval, and a subsequent identical request must not be released".

### 2.6 Agent operation evidence recording —— already present (fields need extension)

- **Current state**: `ActionLedger` is append-only with a hash chain and `verify` (`ledger.py:128/163/179`);
  `_record` (`supervisor.py:174`) lands `op_id/run_id/entry/source/action_type/tool/target/intent_id/
  scope/checks/result/error_code/error_text/evidence/ticket/pid`; the evidence bundle is `_write_bundle` (`:621`).
- **What it covers**: the ledger chain, action-level fields, evidence bundles, ticket snapshots.
- **What it does not cover**: `agent_id`, `agent_status`, `capability`, `request_sha256`, `rule_id` (at action-record level),
  `approval` placeholder, `exception`.
- **Conclusion**: the ledger capability is **reused directly**; only record fields are extended, no new ledger is created.

### 2.7 Agent onboarding adapter —— partially present

- **Current state**: `PersonalAdapter` (`personal_adapter.py:66`) mounts personal's MCP tools:
  `map_tool` (`:126`) performs tool→action mapping, `invoke` (`:139`) and `_gated` (`:199`) handle different modes;
  `loader.py:14` `mode`, `:20` `is_enabled`, `:24` `load_if_enabled` control off-by-default and lazy import.
- **What it covers**: the adaptation paradigm of one real host (personal MCP): off by default, a single mount point, a mapping table.
- **What it does not cover**: a general Agent adapter contract (any Agent submitting `req/1`), onboarding of community/minimal,
  Agent-side identity injection.
- **Conclusion**: the adapter **pattern is reusable**, but its coverage is only one end: personal.

### 2.8 Governance status and query console —— partially present

- **Current state**: `Supervisor.status()` (`supervisor.py:775`) outputs the runtime status;
  `gate_count.py:166` `count_edition` / `:242` `main` counts gates;
  `engine.py:663` `cmd_show`, `:430` `cmd_check` output health checks.
- **What it covers**: CLI text-level status and counts.
- **What it does not cover**: a read-only query surface (query by `agent_id/op_id/decision/time`), visualization of chain integrity,
  the pending-approval queue, pages / console.
- **Risk**: if 0.3 directly reuses `status()` as the "console", internal runtime state would be exposed as governance queries, which is semantically wrong.

## IV. Conflict list (requires the user's ruling; do not decide on your own)

### Conflict C1: Agent unified request interface vs "the kernel provides no service/SDK/IPC"

- Basis: `bumao_core/HOST_CONTRACT.md:156-168`, especially `:162`
  "any service/SDK/IPC | no `http`/`socket`/`grpc`/`daemon`/`server`/`api` anywhere inside the kernel's `.py` files",
  `:168` "it is not an application runtime… it is only called to do one check".
- Conflict point: if 0.3's "unified operation request interface", "Agent onboarding adapter" and "governance query console" are built as
  an external service/SDK/IPC, they directly contradict the hard boundaries above.
- Consequence of not ruling: once the implementation approach is chosen wrongly (in-process API or service), it either violates the contract or overturns the plan.
- Awaiting the user's ruling: whether 0.3's "interface" is restricted to **in-process Python calls** (with no http/socket/grpc/daemon/server/api).

### Conflict C2: Agent identity system vs "the 12-member contract" containing no Agent

- Basis: the 12-member contract at `HOST_CONTRACT.md:104` and the member table in the main text (`:89-91`).
- Conflict point: among the 12 members there is no member slot for Agent identity/capability; if 0.3 adds Agent registration and capability registration
  and requires the host to implement a new member, that amounts to **expanding the contract**.
- Awaiting the user's ruling: whether the new member is an "optional extension" (with a `getattr` fallback) or is upgraded to a contract requirement (which would break the existing three clients).

### Conflict C3: Five-value decision vs 0.2's four-value result convention

- Basis: `result ∈ {ok, denied, error, interrupted}` at `supervisor.py:157/460/492/518/764`.
- Conflict point: 0.3 requires `ALLOW/DENY/REQUIRE_APPROVAL/WARNING/ERROR`; directly changing the value domain of 0.2's `result`
  would touch the existing criteria and the ticket surface (the user has explicitly ordered that the criteria must not be changed).
- Awaiting the user's ruling: whether the five values should be **a new field** (such as `decision`) coexisting with `result`, rather than a replacement.

### Conflict C4: `rule_id` among the four foreign keys vs the action record not actually landing `rule_id`

- Basis: `ledger.py:6` claims five association keys including `rule_id`; `:104` only reads it in the ticket snapshot;
  the action record at `supervisor.py:177-197` has no `rule_id`.
- Conflict point: if 0.3 is designed according to "four foreign keys complete", the missing `rule_id` will be discovered at the action-record layer, which conflicts with the documented convention.
- Awaiting the user's ruling: whether to "add it to the action record", or to "change the existing documented convention to the ticket-snapshot layer".
