以下是内和0.3 的规划：我认为，Bumao Core 0.3 应该正式进入「AI Agent 接入与执行前治理」阶段。

这是 Core 从一个可复用的规则执行与治理框架，向真正面向 AI Agent 的通用治理基础设施迈进的关键版本。

但我先划清楚边界：0.3 不应该直接追求全面监管 AI Agent。那是更后面的运行时治理能力。否则很容易把项目做得过大。

Bumao Core 0.3 功能规划

建议版本定位

AI Agent 接入与执行治理

核心目标：让不同来源的 AI Agent 能够接入统一治理内核，在执行操作之前接受规则审查，并产生可追溯的治理结果。

0.1：最小治理内核 → 0.2：可复用规则执行与治理框架 → 0.3：Agent 接入与执行前治理

一、0.3 应当实现的八项核心功能

1. Agent 注册与身份管理

让 Core 能够识别接入的 AI Agent。

应实现：

* Agent 注册、注销。
* Agent 唯一 ID。
* Agent 名称、版本、来源。
* Agent 类型与运行环境登记。
* Agent 状态管理。
* Agent 接入信息查询。

例如：

Agent	类型	状态
Desktop Agent	电脑操作	已注册
GIS Agent	GIS 辅助作业	已注册
Coding Agent	编程辅助	已注册

注意：注册不代表可信任，更不代表获得所有操作权限。

2. Agent 能力登记

让 Core 知道一个 Agent 声称自己能够做什么。

例如：

* 文件读取。
* 文件写入。
* 文件删除。
* 网络访问。
* 软件启动。
* 命令执行。
* 数据库访问。
* 测绘数据处理。

每个 Agent 都需要声明能力范围。

核心原则：Agent 声称具备某项能力，不等于 Core 自动允许它使用该能力。

3. 统一操作请求接口

这是 0.3 非常重要的功能。

不同厂商的 Agent，操作请求格式各不相同。

Core 应该建立统一的操作请求结构。

例如，一个 Agent 想删除文件，向 Core 提交：

* 谁发起的操作？
* 要执行什么操作？
* 操作对象是什么？
* 为什么执行？
* 涉及哪些资源？
* 预期结果是什么？

Core 不需要理解每家 Agent 内部的运行机制，只需要理解统一的请求结构。

4. 执行前规则审查

这是 0.3 的核心治理功能。

Agent 提交操作请求后，Core 根据规则判断：

判断结果	含义
ALLOW	规则允许
DENY	规则禁止
REQUIRE_APPROVAL	需要人工批准
WARNING	存在风险提示
ERROR	审查过程异常

例如：

Agent 请求读取指定文件，规则允许，则返回 ALLOW。

Agent 请求删除重要文件，规则要求人工审批，则返回 REQUIRE_APPROVAL。

注意：返回 ALLOW 只是治理决策，不代表操作已经执行成功。

5. 人工审批接口

0.3 可以开始建立最小审批机制。

需要实现：

* 审批请求生成。
* 审批对象展示。
* 同意或拒绝。
* 审批人记录。
* 审批时间记录。
* 审批结果留档。

但暂时不必做复杂的企业级多级审批、组织架构和多人会签。

6. Agent 操作证据记录

每次治理请求都应当形成记录。

至少包含：

* Agent 身份。
* 操作请求。
* 请求时间。
* 规则版本。
* 命中规则。
* 治理判断。
* 审批结果。
* 执行回执（如果接入方提供）。
* 异常信息。

这里要区分三个概念：

治理请求、治理决策、实际执行结果。

不能把规则审查通过当成实际操作成功。

7. Agent 接入适配器

不同 Agent 需要通过统一适配接口接入 Core。

建议支持：

* 标准化 Agent Adapter。
* 请求格式转换。
* 响应格式转换。
* 身份映射。
* 错误处理。
* 接入状态检测。

0.3 不需要一次兼容所有 AI 厂商。

先做一个标准 Adapter，再提供一个示例 Agent 接入实现即可。

8. 治理状态与查询控制台

让使用者看得见 Core 做了什么。

建议新增：

* Agent 列表。
* Agent 能力列表。
* 操作请求列表。
* 治理决策列表。
* 待审批列表。
* 风险事件列表。
* Agent 接入状态。
* 治理记录查询。

二、0.3 的核心工作流程

AI Agent 发起操作请求

例如：读取、修改、删除文件

Agent 身份与能力识别

Core 统一操作请求解析

规则审查与风险判断

ALLOW

允许进入执行环节

审批

等待人工决定

DENY

拒绝请求

治理结果与证据留档

这里的执行环节需要特别说明：0.3 可以提供标准化的执行授权结果和适配接口，但不能宣称已经能够拦截所有 Agent 的真实操作。实际执行是否受控，取决于 Agent 是否通过受治理的执行适配器调用工具。

三、0.3 暂时不要做什么？

我反而认为，这部分比功能清单更重要。

暂缓功能	原因	建议版本
全过程实时行为监控	需要运行时监督机制	0.4
任意软件操作强制拦截	需要系统级执行控制	0.4 以后
Agent 自主长期目标监管	涉及复杂运行时状态	1.0 以后
多 Agent 协同调度	会引入编排系统	后续
企业级多租户管理	需要组织和隔离体系	商业版阶段
云端统一策略下发	需要云端架构与安全机制	后续

四、0.3 的验收标准

我建议至少设置以下十项验收条件：

* 能够注册和注销 Agent。
* 能够识别 Agent 身份。
* 能够登记 Agent 声明的能力。
* 能够接收统一格式的操作请求。
* 能够调用现有规则治理体系进行审查。
* 能够返回明确的治理决策。
* 能够生成和处理人工审批请求。
* 能够记录完整的治理证据。
* 能够通过标准 Adapter 接入至少一个示例 Agent。
* 能够查询治理请求、决策和审批历史。

每项都需要自动化测试和实际运行验证，不能只以代码文件存在作为完成标准。

五、0.1 到 1.0 的版本路线

* 0.1 — 最小治理内核
    建立规则、配置、闸门、基础治理结构。
* 0.2 — 可复用治理框架
    形成规则执行、宿主契约、扩展机制和治理结果体系。
    当前已发布 Beta 版本
* 0.3 — Agent 接入与执行前治理
    让不同 AI Agent 能够接入 Core，提交操作请求，接受规则审查。
    下一阶段目标
* 0.4 — 执行过程监督与权限控制
    进一步将治理从执行前扩展到执行中，建立更可靠的实际执行约束。
* 1.0 — 稳定通用 AI 治理运行时
    形成经过实际使用验证、接口稳定、具备可靠执行治理能力的通用内核。

六、我对 0.3 最重要的一个判断

你现在的 Core 已经有规则执行和治理框架，但它还没有真正解决一个关键问题：

AI Agent 在实际工作时，如何把自己的操作交给一个独立的治理内核判断？

0.3 就是要解决这个问题。

如果这一步做出来，Core 的定位就会发生一次实质性变化：

* 0.2：能够执行治理规则。
* 0.3：能够接收和审查 AI Agent 的操作请求。
* 0.4：能够进一步监督和约束实际执行。
* 1.0：成为可复用的通用 AI 治理运行时。

这条路线也会给未来的 Bumao GeoOps 提供基础：测绘 Agent 可以使用同一套身份、请求、审查和证据机制，而测绘专业规则仍然由 GeoOps 自己负责。
