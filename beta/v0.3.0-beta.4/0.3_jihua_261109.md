## 1. 目标与硬边界

### 1.1 版本定位

AI Agent 接入与执行治理：让不同来源的 AI Agent 接入统一治理内核，在执行操作前接受规则审查，并产生可追溯的治理结果。

### 1.2 硬边界（原文明确）

- **不追求全面监管**：全过程实时监控、强制拦截属 0.4／0.4 以后，不在 0.3。
- **不得宣称拦截真实操作**：0.3 只提供标准化执行授权结果与适配接口；实际执行是否受控，取决于 Agent 是否通过受治理的执行适配器调用工具。
- **治理决策 ≠ 执行成功**：`ALLOW` 只代表规则允许，不代表操作已执行。
- **注册 ≠ 可信任 ≠ 全权**：Agent 注册与能力声明都不自动赋予权限。
- 工程侧：不改已发布三端行为、不改判据与 `rule_id` 口径、不重写 0.2 的账本链与四外键。

## 1. Goals and hard boundaries

### 1.1 Version positioning

AI Agent onboarding and execution governance: let AI Agents from different sources onboard a unified governance kernel, undergo rule review before executing operations, and produce traceable governance results.

### 1.2 Hard boundaries (explicit in the source text)

- **Does not pursue comprehensive supervision**: full-process real-time monitoring and mandatory interception belong to 0.4 / after 0.4, not 0.3.
- **Must not claim to intercept real operations**: 0.3 only provides standardized pre-execution authorization results and adaptation interfaces; whether actual execution is controlled depends on whether the Agent invokes tools through a governed execution adapter.
- **Governance decision ≠ successful execution**: `ALLOW` only means the rules permit it, not that the operation has been executed.
- **Registration ≠ trustworthy ≠ full authority**: neither Agent registration nor capability declaration automatically grants permissions.
- On the engineering side: do not change the behavior of the three released clients, do not change the criteria or the `rule_id` convention, do not rewrite 0.2's ledger chain and four foreign keys.

## 3. Mapping of the five work flows

The source-text flows are counted as five main stages:

| # | Flow stage | beta1 landing point | Actual measurement evidence | Status |
|---|---|---|---|---|
| 1 | AI Agent initiates an operation request (read/modify/delete) | `request.build` plus `run_beta1.py` STEP 1 | `schema=req/1`, 9 fields | Landed |
| 2 | Agent identity and capability identification | `identity.AgentRegistry.get` / `::capability` plus STEP 2 | `agent-demo active`, `cap-del-approved`, `sig=valid` | Landed (revocation not tested) |
| 3 | Core unified operation request parsing | `request.validate` | REV-5 missing target → `ERROR/INVALID_SCHEMA` | Landed |
| 4 | Rule review and risk judgment | `review.run` | `ALLOW/R0.11`; four types of denial; `REQUIRE_APPROVAL`; `WARNING` | Landed (rules are not core's existing system) |
| 5 | Governance result and evidence archival | `evidence.record` plus `query.by_op` | four foreign keys complete, look-up hit, chain break = none | Landed |

Branch coverage: `ALLOW` (STEP 3), `REQUIRE_APPROVAL` (REV-6 → approved, pending=0), `DENY` (REV-1/2/3/4) have all been actually measured.

**Execution stage**: beta1 has no execution stage, which complies with the source text's limitation that "it cannot claim to intercept real operations"; but for that same reason there is no execution receipt of any kind.

## 7. 0.1 → 1.0 route mapping

| Version | Source-text requirement | Current state / landing point | Status |
|---|---|---|---|
| 0.1 | Minimal governance kernel: rules, configuration, gates, basic governance structure | core already has `bumao_core_rules`/`gate_registry`/`engine`, and the v0.1 tag has been released | Completed |
| 0.2 | Reusable governance framework: rule execution, host contract, extension mechanism, governance result system | `HOST_CONTRACT.md`, `jiancha/` (S gates, ledger, adapters), v0.2.0/0.2.1/0.2.2 tags (0.2.2 has no beta marker) | Completed |

| 1.0 | Stable general-purpose AI governance runtime | No implementation | Not started |

GeoOps reservation: the four mechanisms of identity, request, review and evidence are provided by core, while surveying-domain rules still belong to GeoOps; 0.3 introduces no GeoOps-specific rules.

## 8. Risks and stop conditions

| Risk | Manifestation | Stop condition |
|---|---|---|
| Contract conflict | If 0.3's "unified interface / adapter / console" is built as a service/SDK/IPC, it touches `HOST_CONTRACT.md:162` (no http/socket/grpc/daemon/server/api inside the kernel) | Stop immediately, list the conflict and report it for arbitration; do not make the trade-off on your own |
| Contract expansion | If Agent identity/capability is required to become a mandatory item of the 12-member contract (`HOST_CONTRACT.md:104`) | Same as above |
| Decision value-domain conflict | If the five values directly replace 0.2's four `result` values (`supervisor.py:157/460/492/518/764`) | May only add a `decision` field to coexist; must not change the criteria |
| Falsely claiming "the rule system is already connected" | beta1 ships its own rule package yet this is written up as "invoking the existing system" | Correct immediately according to the facts, and reissue the explanation |
| Treating a decision as execution | Claiming that real operations have been intercepted | Withdraw immediately; the source text explicitly forbids it |
| Building a second ledger | Creating a ledger parallel to `ActionLedger` | Stop immediately and switch to reuse |
